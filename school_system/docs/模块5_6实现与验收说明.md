# 模块5/6：同伴互评与助教过程检查

## 实现依据与范围

依据最终《需求分析报告.md》及功能清单中“检查与互评负责人”职责，实现：

- **模块5（同伴互评）**：教师确认被评版本、自动分配及手动调整任务、评审待办与填写提交、进度查询、取消与延长、反馈开放、复核申请与重评。
- **模块6（助教过程检查）**：授权范围内的检查列表、查看进度及成果、记录检查结论和反馈、整改复查、缺交迟交与问题上报。

入口为 `/modules/reviews?courseId=1`。后端代码位于 `backend/src/main/java/cn/edu/school/review/`（模块5）与 `cn/edu/school/inspection/`（模块6），数据库迁移为 `V4__review_inspection.sql`，前端为 `frontend/src/views/ReviewView.vue` 与 `frontend/src/api/reviews.ts`。

## 使用与权限

| 账号 | 权限 |
|---|---|
| teacher01 | 课程教师：创建互评批次、自动/手动分配、取消任务、延长截止、关闭批次、开放/关闭反馈、处理复核（同意重评或驳回）。只读查看助教检查与问题上报。 |
| student01 | 甲组负责人：填写本人互评待办、查看本团队收到的匿名互评、对本团队成果申请复核。 |
| student03 | 甲组成员：填写本人互评待办、查看匿名反馈；仅负责人可申请复核。 |
| assistant01 | 课程助教：针对具体版本记录检查结论、整改反馈、复查与问题上报；不能正式评分，不参与互评分配。 |
| student04 / student05 / student06 | 乙组、丙组负责人/成员，按上述学生规则参与互评与查看本团队检查记录。 |
| admin01 | 不自动取得课程业务权限。 |

默认演示密码沿用 `Demo@2026!`。演示项目“检查与互评（演示）”已预置甲组（student01+student03）、乙组（student04）、丙组（student05+student06）三个团队，每队均已具备教师确认的被评版本，可直接创建批次并自动分配。

## 数据模型（V4）

- `review_round`：互评批次，含名称、截止时间、状态（OPEN/CLOSED）、反馈是否开放。
- `review_task`：一次分配，固定指向某被评引用与评审人，状态（PENDING/SUBMITTED/CANCELLED），`reevaluation` 标记是否为重评。
- `review_submission`：评审结果，`task_id` 唯一，分数 0–100，评语必填。
- `review_appeal`：复核申请，含被评引用、申请团队、原因、状态（PENDING/APPROVED/REJECTED）、处理意见。
- `inspection`：助教检查记录，固定指向具体版本，含结论、反馈、整改要求、问题上报、`parent_id` 指向被复查的旧检查。

## 关键业务规则

### 模块5

- **禁止自评**：自动分配与手动添加均跳过评审人所在团队；服务端再次校验 `gateway.member(teamId, reviewerId)`。
- **每人默认评2个其他团队**：自动分配只面向本项目的在队学生，按团队顺序跳过本人团队、取前两个，结果确定且幂等（重复分配不产生新任务）。
- **固定成果及标准版本**：任务保存 `submission_review_binding.id`（教师确认的不可变被评版本），不随重交而漂移。分配时通过 `submission_review_access` 授予评审人该精确版本的读取授权，取消或关闭批次时关闭授权。
- **对学生隐藏评审人身份**：学生端“收到的互评反馈”仅展示匿名分数与评语。
- **提交校验**：分数 0–100、评语非空且 ≤2000、截止前、仅本人待处理任务；提交后不可修改。
- **进度查询**：教师端按批次查看每项任务的评审人、被评团队、状态、分数与评语。
- **取消与延长**：教师可取消待处理任务（收回读取授权）；延长须晚于当前截止；关闭批次会把剩余待处理任务置为取消。
- **反馈开放**：教师开放后，团队才能看到已提交的匿名反馈；否则“收到的互评反馈”为空。
- **复核与重评**：仅团队负责人可为本人团队申请复核，且须已有互评结果；同一引用仅一个待处理申请。教师同意后新增一次 `reevaluation=TRUE` 的重评任务并保留原结果（历史不覆盖），驳回则记录处理意见。

### 模块6

- **检查关联具体版本**：每次检查保存 `version_id`，复查通过 `parent_id` 引用旧检查；成员准备整改材料后由负责人正式重交，助教针对新版复查。
- **记录结论与反馈**：结论必填；要求整改或上报问题时反馈必填，否则不允许落库。
- **整改复查**：助教对“要求整改”的记录可发起“针对新版复查”，产生带 `parent_id` 的新检查。
- **缺交、迟交及问题上报**：勾选“问题上报”使记录带上 `reported` 标记，教师可在团队工作空间查看。
- **助教不能正式评分**：仅 `TA` 角色可新建检查，教师/学生只读；评分与成绩仍由后续计分模块实现。
- **检查通过不是互评的强制前提**：两者独立，互评只依赖“已确认的被评版本”。

## 与模块4对接

- 复用 `submission_review_binding` 作为固定被评引用，复用 `submission_review_access` 作为评审人精确版本授权；模块5的 `grantAccess`/`revokeAccess` 直接读写该表。
- 模块4的下载入口 `GET /api/submissions/teams/{team}/versions/{id}/files/{material}` 按该精确版本授权，模块5授予的评审人可下载被评材料，但不可读取团队待提交区或其他版本。
- `inspection.version_id` 指向 `submission_version.id`，可追溯具体版本、受理时间与提交人。

## API摘要

### `/api/reviews`

| 方法与路径 | 功能 |
|---|---|
| GET `/projects?courseId={id}` | 课程内可见项目及批次、被评版本、本人待办计数 |
| GET `/projects/{project}` | 工作空间：被评版本、批次、本人待办、匿名反馈、复核、进度（教师）、学生名单（教师） |
| POST `/projects/{project}/rounds` | 教师创建互评批次 `{name, deadline}` |
| POST `/rounds/{round}/assign` | 教师自动分配（每人2个其他团队） |
| POST `/rounds/{round}/tasks` | 教师手动添加任务 `{reviewerId, bindingId}` |
| POST `/tasks/{task}/cancel` | 教师取消待处理任务并收回授权 |
| POST `/rounds/{round}/extend` | 教师延长截止 `{deadline}` |
| POST `/rounds/{round}/close` | 教师关闭批次（取消剩余待处理任务） |
| POST `/rounds/{round}/feedback` | 教师开放/关闭反馈 `{open}` |
| POST `/tasks/{task}/submit` | 学生提交互评 `{score, comment}` |
| POST `/appeals` | 负责人申请复核 `{bindingId, reason}` |
| POST `/appeals/{appeal}/approve` | 教师同意复核并安排重评 `{reviewerId, resolution}` |
| POST `/appeals/{appeal}/reject` | 教师驳回复核 `{resolution}` |

### `/api/inspections`

| 方法与路径 | 功能 |
|---|---|
| GET `/teams?courseId={id}` | 课程内可见团队（学生仅本团队） |
| GET `/teams/{team}` | 工作空间：版本、被评引用、检查记录、角色与整改/上报标记 |
| POST `/teams/{team}` | 助教记录检查 `{versionId, conclusion, feedback, rectificationRequired, reported, parentId}` |

## 可重复验收流程（对应“助教完成一次检查，两名学生完成指定互评”）

使用“检查与互评（演示）／课程1 软件工程”。

### 助教过程检查（模块6）

1. assistant01 打开“检查与互评 → 助教检查”，选择“评审演示·甲组（演示）”。
2. 点击“新建检查”，选择具体版本（如 v1），填写结论“初检发现缺少单元测试”，勾选“需要整改”并填写反馈“补充测试后由负责人正式重交”。
3. 确认后检查记录出现，带“要求整改”标记；teacher01 与 student01 均只读可见。
4. 成员整改后由 student01 正式重交新版，assistant01 再次“针对新版复查”，记录“复查通过”；新记录带 `parent_id`，旧检查保留。

### 同伴互评（模块5）

1. teacher01 打开“检查与互评 → 同伴互评”，选择“检查与互评（演示）”项目。
2. 点击“创建互评批次”，填写批次名称与截止时间（北京时间）。
3. 在批次上点击“自动分配（每人2个其他团队）”：甲组 student01/student03 各自收到乙、丙两个团队的被评任务，且不含本团队。
4. 至少两名学生完成指定互评：student01 在“我的互评待办”中查看被评成果，填写 0–100 分与评语并提交；student04 同样提交本人待办。教师进度页可见两者状态变为“已提交”并看到分数与评语。
5. 教师点击“开放反馈”后，student01 在“本团队收到的互评反馈”看到匿名分数与评语。
6. 甲组 student01 可“申请复核”；teacher01 在“复核申请”中同意并选择一名未评审过甲组的学生作为重评人，系统新增重评任务且原评分保留；或驳回并记录意见。

演示项目会保留实际记录；不得为重复练习删除旧版本或改写历史。可在新批次继续练习，旧批次关闭后待处理任务自动取消。

## 验证记录

后端新增 9 项集成测试（`ReviewInspectionIntegrationTest`），全量 62 项测试通过。覆盖：助教检查与整改复查、自动分配确定性（每人2个其他团队、禁止自评、幂等）、两名学生提交指定互评、越权与分数/评语校验、截止与延长、关闭批次收回授权、复核同意重评且保留历史、复核驳回、检查的角色/版本/反馈约束、审计失败回滚。

前端 `ReviewView.vue` 已通过 `vue-tsc --noEmit` 类型检查。测试运行使用 H2，真实 PostgreSQL 联调仍按后续数据库方案执行；数据库 V4 采用新增表和外键，升级前请在本机 `.runtime/backups/` 保存迁移前演示库备份。
