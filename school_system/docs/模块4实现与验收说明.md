# 模块4：成果提交与版本管理

## 实现依据与范围

依据最终《需求分析报告.md》§3.5、§5.7.2、§6.3及AC-04、AC-15，实现材料准备、正式提交与重交、版本详情、授权下载、回执、最终指定、截止冻结、未指定异常核实及限时补交。

入口为 `/modules/submissions?courseId=1`。实际代码在 `feat/tasks-submissions` 分支的 `school_system` 目录中，使用现有登录会话、CSRF、课程权限、文件存储与管理审计。

## 使用与权限

| 账号 | 权限 |
|---|---|
| student01 | 团队负责人：准备材料、正式提交及重交、指定最终成果、申请补交。 |
| student03 | 同团队成员：准备材料、查看版本、下载授权材料；不能正式提交或指定最终成果。 |
| teacher01 | 课程教师：查看团队成果、处理未指定异常、确认具体被评版本、批准或拒绝补交申请。 |
| assistant01 | 课程授权范围只读，不代替负责人提交，不改变最终引用，不审批补交。 |
| student04 | 其他团队负责人，默认不能读取本团队成果；模块C实际分配指定版本后按对应授权读取。 |
| admin01 | 不自动取得课程业务权限；可读取仅含事件编号、尝试次数及状态的通知故障队列。 |

默认演示密码沿用 `Demo@2026!`；配置过 `DEMO_PASSWORD` 时使用配置值。

## 三种引用与不可覆盖的版本

1. **本轮当前有效版本**：每个“团队＋迭代”只有一个成果包，成功重交使其当前引用更新为新版本。
2. **项目最终成果**：负责人主动选择本团队任意迭代中已提交的具体版本；截止前可重新指定并记录前后内容。
3. **教师确认的被评版本**：教师在最终交付后确认具体版本，形成独立、不可改写的评审引用记录。

重交只改变第一项，不自动更换最终指定或已有被评引用。正式版本保存材料快照、实际提交人、真实受理时间、当时截止依据、文件总量和回执；不提供正式版本编辑、覆盖或撤回入口。移出待提交材料区不删除已提交版本文件。

## 材料与提交校验

- 允许PDF、DOCX、PPTX、XLSX、TXT、MD、PNG、JPG/JPEG、ZIP；单文件大于0且不超过50 MB，每个版本文件总量不超过200 MB。
- 外部链接须为有效HTTPS地址，不含嵌入式账号密码；代码链接填写提交编号或标签。系统记录链接，不请求外部网页；教师确认可访问性。
- 材料属于具体团队和迭代。成员可上传本团队材料；负责人选取材料并填写成果说明后执行正式提交。
- 校验材料存在及文件完整性后记录成功受理时间。等于最终截止仍按时，超过截止只能使用当前团队有效授权窗口，不回填受理时间。
- 每次主动提交使用新请求编号；网络响应不确定时可查询回执或以同一请求编号重试。相同请求只返回原回执，同一编号对应不同内容时返回冲突。
- 业务数据、材料快照、过程记录和管理审计一起提交；必要记录保存失败则回滚。上传失败或事务回滚时清理本次新建物理文件。

## 截止、核实与授权补交

后台每10秒检查到期团队；页面访问和相关操作也核对期限。截止事件独立于是否提交或指定：固定已有最终引用，未指定则保留异常，不自动选取最新版本。

负责人截止后填写补交或整改原因；教师可批准申请，或针对当前团队直接建立窗口。窗口开始不早于项目最终截止、结束晚于开始且尚未结束，每次最长7个自然日；结束时刻不属于开放窗口。终止、归档或草稿项目不接受新增成果操作。

补交产生新的版本、真实受理时间和迟交标记，不自动扣分，不改写冻结引用。未指定的由教师选择具体版本、确认材料可访问并填写核实依据。需要改变已有被评版本时，教师明确勾选“需安排重评”，新增引用记录，旧引用保留；实际评审任务由模块C安排。

## 可重复验收流程

### 普通交付

使用“课程项目协作平台（模块3演示）／基因重组（演示）”。在模块3新建或选择一轮迭代。

1. student03上传一个小型MD/PDF文件，添加HTTPS代码仓库链接及标签，例如仓库链接与标签 `v1.0`。
2. student01选择同一迭代，全选材料，填写“第一版：完成本轮功能”，正式提交。
3. 检查回执、v1版本、受理时间、提交人；下载文件并核对原内容。
4. 指定v1为最终成果。
5. 返回准备区上传修订文件，填写“第二版：修正异常处理”，正式重交。
6. 确认出现v2、v1仍可下载，本轮当前版本为v2，最终指定仍为v1。
7. 主动重新指定v2，刷新后核对引用及历史。

### 截止后补交与教师核实

使用独立的“成果补交与异常核实验收（演示）／基因重组·截止后验收（演示）”，其期限在首次生成时已过，不改变普通演示项目与用户已有数据。该项目含一轮已结束的“截止后成果验收”迭代。

1. 无有效授权窗口时，负责人只能查看历史，普通上传与提交关闭；可以申请补交。
2. student01申请补交，例如“上传故障，申请两天内补交”。
3. teacher01在“补交与确认记录”批准，填写北京时间起止时间和授权原因，窗口不超过7天。
4. student01刷新页面，在授权窗口内准备材料并提交；回执应标为授权迟交，不自动扣分。
5. 最终指定仍为空时，teacher01在版本列表处理“核实未指定异常”，选择具体版本、确认可访问并填写理由。
6. teacher01单独“确认被评版本”；之后负责人再次重交，核对最终指定和原被评引用均未自动改变。
7. 如确需更换被评版本，teacher01选择新版本、勾选需安排重评并填写原因；检查旧引用历史仍在。

演示项目会保留实际验收记录。若已有有效补交窗口或教师核实记录，可先查看既有记录，再继续新的合法补交与确认操作；不得为重复练习删除旧版本或改写历史受理时间。

## 与C、D模块对接

- `submission_package.current_version_id`：某团队迭代的最新有效版本。
- `team_delivery.final_version_id`：项目最终指定；`frozen_at`、`frozen_deadline`保存截止冻结信息。
- `submission_review_binding`：每次教师确认的不可变被评版本引用。C的评审任务应保存其 `id` 或对应固定 `version_id`，不能从当前最新版本动态推导。
- `submission_review_access`：C维护具体被评引用的评审人授权，取消或失效时将 `active` 关闭。模块4下载入口按该精确版本授权，不扩大到其他版本、待提交区或团队工作空间。
- `submission_version`及`submission_version_material`：D可按固定版本追溯材料、受理时间和截止依据；计分名单、评分及成绩发布仍由相应模块实现。
- 模块4的站内通知通过 `submission_event` 投递到 `submission_notice`，后续公共通知模块可整合这些事件；应复用事件编号，避免重复通知。

## API摘要

接口前缀 `/api/submissions`。

| 方法与路径 | 功能 |
|---|---|
| GET `/teams/{team}` | 工作空间、权限、材料、版本、引用、窗口和本人消息 |
| POST `/teams/{team}/materials/files` | 上传团队待提交文件，表单含iterationId、revision、file |
| POST `/teams/{team}/materials/links` | 保存HTTPS链接及代码标签 |
| POST `/teams/{team}/materials/{id}/remove` | 移出待提交区，保留正式版本材料 |
| GET `/teams/{team}/materials/{id}/download` | 授权读取待提交文件 |
| POST `/teams/{team}/versions` | 正式提交、主动重交或同请求重试 |
| GET `/teams/{team}/versions/{id}` | 具体版本与回执 |
| GET `/teams/{team}/versions/{id}/files/{material}` | 按具体版本授权下载 |
| GET `/teams/{team}/receipts/{requestKey}` | 按请求编号查询受理结果 |
| POST `/teams/{team}/final-selection` | 负责人截止前主动指定或重新指定 |
| POST `/teams/{team}/verify-final` | 教师核实未指定异常 |
| POST `/teams/{team}/review-bindings` | 教师确认被评版本并保留引用历史 |
| POST `/teams/{team}/extension-requests` | 负责人申请补交 |
| POST `/teams/{team}/extensions` | 教师授权窗口 |
| POST `/teams/{team}/extension-requests/{id}/reject` | 教师拒绝申请并记录原因 |
| GET `/teams/{team}/history?beforeId={id}` | 游标分页读取过程记录 |
| POST `/teams/{team}/notices/{id}/read` | 本人消息标记已读 |
| GET `/notice-failures` | 管理员读取脱离业务内容的通知故障队列 |

写操作沿用团队 `revision` 防止旧页面覆盖新数据，使用同一团队行锁串行确认写入。文件、版本及材料下载逐次检查当前课程身份、团队关系或指定版本的评审授权。通知后台独立事务投递，同一事件同一接收人仅一份；首次失败后重试3次，仍失败进入管理员故障队列。
