# 模块3：迭代、团队任务与里程碑

## 实现范围与依据

需求依据：最终《需求分析报告.md》§3.4、§5.4、§6.2，FR-009—FR-012、UC-03、UC-04、AC-03。代码位于 `feat/tasks-submissions` 分支。

| 需求 | 当前实现 |
|---|---|
| FR-009 | 负责人创建、修改本团队迭代，维护目标、计划日期和迭代顺序；不同团队独立管理。 |
| FR-010 | 每项任务关联本团队迭代、同项目要求及有效执行成员；负责人维护分工，教师记录原因后可干预任务。 |
| FR-011 | 普通成员只更新本人任务；负责人可管理本团队任务；状态为未开始、进行中、已完成，返工返回进行中并填写原因。 |
| FR-012 | 显示任务汇总、里程碑日期及完成情况；负责人手动开始和结束迭代，结束须填写完成情况，有未完成任务时填写遗留事项；未完成任务可转入后续迭代。 |

计划到期不会触发自动结束或延期标记；没有任务时显示“尚无任务，进度未形成”。项目处于草稿、已结束、已终止、已归档或已超过最终截止时，禁止修改协作信息。已结束迭代不再修改计划或进度，仍可将遗留任务转入后续迭代。

## 页面与演示账号

前后端启动后访问 `/modules/tasks?courseId=1`，也可从课程空间的“迭代与任务”进入。

| 账号 | 用途 |
|---|---|
| student01 | 演示团队负责人：管理迭代、任务、里程碑。 |
| student03 | 同团队普通成员：查看进度、更新分配给本人的任务。 |
| student04 | 另一团队负责人：验证团队数据隔离。 |
| teacher01 | 课程教师：查看课程团队并记录原因后干预任务。 |
| assistant01 | 本课程助教：查看课程授权范围内团队进度，不修改协作数据。 |
| student02 / admin01 | 验证跨课程访问与管理员不自动获得课程业务权限。 |

本地默认密码沿用框架设置；默认值为 `Demo@2026!`，配置 `DEMO_PASSWORD` 后使用配置值。演示项目与团队在页面上明确标注，种子数据仅在 `demo & !postgres` 环境生成，不新增项目发布、组队审批等模块A功能。种子程序在已有框架账号与课程完成初始化后执行，仅首次补充演示项目。

操作顺序：负责人新建迭代并开始 → 新建任务、选择项目要求和成员 → 设置里程碑 → 普通成员更新本人任务 → 负责人记录完成情况及遗留事项并结束迭代 → 必要时将未完成任务转入后续迭代。刷新页面后数据仍保留。

## 与A模块的对接边界

当前主线只有框架，没有已实现的项目与团队业务表。V2迁移补入模块3必要的只读关联基础：

- `course_project`：课程、项目名称、状态、最终截止和演示标记。
- `project_requirement`：教师项目要求。
- `project_team`：项目、团队名称、负责人及协作修订号。
- `project_team_member`：团队有效成员关系。

上述信息通过 `ProjectTeamGateway` 读取；模块3不提供它们的创建、发布、审批、转组等管理接口。A模块合并时，应复用这些身份与关联，或替换 `JdbcProjectTeamGateway` 并迁移外键，保持同一项目、团队、成员标识，不保留两套相互独立的业务身份。

项目状态代码为 `DRAFT / PUBLISHED / IN_PROGRESS / ENDED / TERMINATED / ARCHIVED`。课程权限仍使用框架的 `CoursePermission`。课程内的助教身份在本版表示课程范围检查授权；以后若A/C模块增加项目级助教授权，应在网关中收窄读取范围。

迁移V2已用于本地演示与测试。其他分支合并前须核对迁移版本号，不能覆盖已应用迁移；后续结构变更追加新迁移。A模块对负责人、有效成员关系及项目状态的写操作应与模块3的团队行锁协调，防止权限变更与业务写入相互穿越。

## API契约

接口前缀 `/api/collaboration`，沿用现有登录会话、CSRF保护和响应格式。

| 方法与路径 | 行为 |
|---|---|
| GET `/teams?courseId={id}` | 返回授权课程内可访问团队；学生仅本团队，教师/助教按课程授权读取。 |
| GET `/teams/{team}` | 团队工作空间、权限标识、当前修订号、成员、项目要求、迭代、任务和里程碑。 |
| POST `/teams/{team}/iterations` | 新建迭代。 |
| PUT `/teams/{team}/iterations/{id}` | 修改迭代目标、日期和顺序。 |
| POST `/teams/{team}/iterations/{id}/start` | 负责人手动开始。 |
| POST `/teams/{team}/iterations/{id}/end` | 负责人手动结束并记录总结、遗留事项。 |
| POST `/teams/{team}/tasks` | 新建关联迭代和项目要求的任务。 |
| PUT `/teams/{team}/tasks/{id}` | 调整任务内容、执行人及计划。 |
| POST `/teams/{team}/tasks/{id}/progress` | 更新状态与进展说明，返工须填写原因。 |
| POST `/teams/{team}/tasks/{id}/move` | 未完成任务转入本团队顺序更后的未结束迭代，保留最初归属和每次迁移记录。 |
| POST `/teams/{team}/milestones` | 新建里程碑。 |
| PUT `/teams/{team}/milestones/{id}` | 更新完成条件、日期与完成结果。 |
| GET `/teams/{team}/history?beforeId={id}` | 每次最多50条团队过程记录，可按游标查看更早记录。 |

写操作提交最近一次工作空间返回的 `team.revision` 作为 `revision`。后端锁定团队行并核对修订号，保存成功后修订号加一；旧页面写入返回409 `STALE_WORKSPACE`，客户端刷新后重新操作。任务和里程碑计划日期须位于所属迭代范围内，迭代计划不能超过项目最终截止日期（北京时间）。同一团队迭代顺序不重复。

团队过程记录包含对象、操作者、时间、操作原因及变更前后数据，可供有效团队成员查看；同时写入框架管理审计记录。业务数据、过程记录、审计及修订号在同一事务内保存，必要记录写入失败时整体回滚。

## 模块4与其他后续对接

模块4应复用 `team_iteration.id`，成果包按团队和迭代关联；本次不加入正式提交、版本冻结和补交功能。模块3的 `collaboration_event` 可供过程检查引用。站内通知尚由公共通知模块后续对接，当前页面刷新读取最新进度；本模块不另行实现通知渠道。
