# 1 项目概述与设计目标

## 1.1 项目定位

平台面向项目制课程，支持教师发布课程项目、学生组队与选题、团队协作迭代、成果提交与版本管理、助教检查、同伴互评、教师评分及成绩发布。平台以课程为组织边界，以项目和团队为主要业务对象，并通过版本、评审引用和成绩记录保留过程依据。

## 1.2 设计目标

1. 职责分离：前端负责页面呈现和交互，后端负责身份识别、权限校验、业务规则执行和数据持久化。
2. 业务闭环：以项目为业务主线，将团队、迭代、任务、成果版本、检查、互评和成绩串联起来。
3. 数据可追溯：正式提交生成独立版本和回执；最终成果指定、被评版本确认、评分和成绩发布分别留存记录。
4. 权限可控：课程成员身份、团队成员关系、团队负责人身份和助教团队授权共同决定操作范围。
5. 运行可复现：支持 Windows 本地前后端独立启动，使用 H2 文件数据库进行课程演示；同时提供 PostgreSQL/Docker 部署配置。

## 1.3 设计范围

| 范围 | 当前系统设计内容 |
| --- | --- |
| 用户与课程 | 账号认证、课程成员关系、教师/助教/学生课程角色、平台管理员基础管理 |
| 课程项目 | 项目池、项目要求、项目状态、评分维度及权重配置 |
| 组队与协作 | 课程内固定团队、邀请确认、项目选题、迭代、任务、里程碑和过程记录 |
| 成果交付 | 材料准备、正式提交、版本、回执、最终成果指定、被评版本确认、截止后授权补交 |
| 检查与评审 | 助教检查与复查、教师组织互评、学生提交互评、复核与重评 |
| 评分与成绩 | 教师评分、互评汇总、名单核对、成绩发布、更正和课程成绩导出 |
| 支撑能力 | 站内通知、操作审计、文件存储、课程数据留存及备份恢复工具 |

# 2 总体架构设计

## 2.1 总体技术架构

系统采用前后端分离的 Web 架构。浏览器运行 Vue 单页应用，前端通过 HTTP API 与 Spring Boot 后端交互；后端通过 Spring Security 完成会话认证和 CSRF 防护，通过业务服务执行规则，再访问关系型数据库和本地附件存储。

| 层次 | 技术/组件 | 主要职责 |
| --- | --- | --- |
| 表示层（浏览器） | Vue 3、TypeScript、Element Plus、Vue Router、Vite | 页面展示、路由、表单交互、当前用户状态管理、调用 API |
| 接口层 | Spring Boot Web、Controller | 接收 `/api` 请求、读取当前登录主体、参数绑定、返回统一响应 |
| 安全层 | Spring Security、Session Cookie、CSRF | 认证、接口访问保护、写操作 CSRF 校验、401/403 处理 |
| 业务层 | 各业务 Service、CoursePermission、AuditService | 业务规则、角色/对象权限、事务控制、操作记录 |
| 数据访问层 | Spring Data JPA、JdbcTemplate、Repository | 实体持久化、查询和更新、事务内 SQL 操作 |
| 数据与文件层 | H2、PostgreSQL、文件目录 | 课程与业务数据持久化；成果文件及待提交材料保存 |

浏览器通过 HTTP 调用后端接口。本地开发时，Vite 将请求代理到 Spring Boot。Spring Security 负责会话认证和 CSRF 校验，Controller 将通过校验的业务请求交给相应 Service。Service 执行业务规则，通过 JPA 或 JdbcTemplate 读写 H2 或 PostgreSQL。数据库保存业务记录和附件元数据，文件服务将附件内容保存到非公开目录。

## 2.2 前后端调用关系

前端 API 模块统一通过 `frontend/src/api/http.ts` 发起请求。业务页面调用对应 API 函数，后端 Controller 接收请求并将当前登录用户 `UserPrincipal` 传入 Service。Service 根据课程、团队、项目和资源状态校验权限及业务条件，完成数据库读写；成功后返回数据，前端根据响应刷新工作区。

本地开发时，Vite 前端运行于 5173 端口，将 `/api` 请求代理到本机 8080 端口的后端服务。用户访问前端页面，不直接访问数据库。文件下载接口按附件响应处理，不按统一 JSON 响应解析。

| `frontend/src/api/` | 按业务域封装 API 请求与 TypeScript 数据类型 |

# 3 前端设计

## 3.1 前端技术组成

前端使用 Vue 3.5.44 构建单页应用，TypeScript 5.9.3 用于类型约束，Vue Router 4.6.4 管理页面路由，Element Plus 2.11.8 提供界面组件，Vite 6.4.5 负责开发服务器和构建。依赖版本以 `frontend/package.json` 与 `package-lock.json` 为准。

| `views/CollaborationView.vue` | 迭代、任务、里程碑及团队过程协作 |

## 3.3 API 封装与状态管理

`frontend/src/api/` 下按业务拆分 `courses`、`projects`、`courseTeams`、`teams`、`collaboration`、`submissions`、`reviews`、`grades` 等 API 文件。页面不应自行拼接数据库操作；业务请求通过 API 层统一封装。`http.ts` 负责请求基础处理，并配合后端 CSRF 约定完成写请求凭证携带。`stores/auth.ts` 保存当前用户会话状态，`stores/workspace.ts` 管理当前课程/项目/团队工作区上下文。

## 3.4 前端职责边界

- 负责展示当前用户可见的课程、团队、版本、评审和成绩数据。
- 负责采集表单输入、发起 API 请求、展示成功结果和业务错误。
- 可以根据后端返回的角色和能力字段控制按钮显示，但该显示控制仅用于交互体验。
- 不能将前端传入的角色、用户 ID 或页面隐藏状态作为权限依据；后端必须重新识别当前用户并校验资源访问权。
- 不能仅凭前端上传成功就认定成果正式提交；正式提交必须调用后端提交接口并取得版本与回执。

# 4 后端设计与模块分工

## 4.1 后端技术组成

后端使用 Java 21 与 Spring Boot 3.5.7，主要依赖包括 Spring Web、Spring Security、Spring Data JPA、Validation、Flyway 11.7.2 和 Apache POI 5.3.0。后端通过 Controller 暴露接口，通过 Service 实现业务逻辑；持久化同时使用 Spring Data JPA Repository 与 JdbcTemplate。数据库结构由 Flyway 迁移脚本维护。

## 4.3 业务服务之间的协作

各业务模块通过共享项目/团队数据和服务接口协作。`ProjectTeamGateway` 为协作、成果、检查、评审和评分等模块提供项目团队数据访问边界，避免各模块各自维护互不关联的项目、团队副本。`CoursePermission` 负责课程成员和课程角色检查；具体模块 Service 再判断团队成员、负责人、助教授权范围及业务状态。

关键写操作由各业务 Service 的事务方法执行。以正式提交为例，系统在同一事务内追加 `AuditService` 操作记录。该设计使业务数据变更与审计记录保持一致；发生事务异常时，数据库事务回滚。

# 5 数据库设计与关键数据关联

## 5.1 数据库总体方案

数据库结构由 `backend/src/main/resources/db/migration/` 下的 Flyway 脚本管理，当前迁移版本包含 V1 至 V14。课程演示默认采用 H2 2.3.232 文件数据库；项目同时提供 PostgreSQL 17.6 Alpine 的 Docker Compose 部署配置。JPA 用于实体映射和部分 Repository 操作，JdbcTemplate 用于业务查询及复杂事务 SQL。

## 5.2 核心数据实体

| 数据主题 | 核心表 | 用途与关联 |
| --- | --- | --- |
| 用户与课程 | `app_user`、`course`、`course_membership` | 用户与课程通过成员关系关联；课程成员关系保存课程角色和有效状态 |
| 课程项目 | `course_project`、`project_requirement`、`project_criterion` | 项目属于课程；项目要求和评分维度依附于项目 |
| 课程团队 | `course_team`、`course_team_member` | 课程内固定团队及邀请/确认成员；课程团队可关联多个所选项目 |
| 项目团队 | `project_team`、`project_team_member` | 项目维度团队交付单元；关联项目、负责人、成员及课程团队 |
| 协作过程 | `team_iteration`、`team_task`、`team_milestone`、`collaboration_event` | 迭代属于项目团队；任务归属迭代；里程碑关联迭代；事件保存过程变更 |
| 成果提交 | `submission_material`、`submission_package`、`submission_version`、`submission_version_material` | 团队准备材料并正式提交；版本材料关联具体提交版本，保留版本历史 |
| 交付状态 | `team_delivery`、`submission_extension_request`、`submission_extension` | 记录团队最终成果、冻结时间、评审引用及截止后补交申请/授权 |
| 检查与互评 | `inspection`、`review_round`、`review_task`、`review_submission`、`review_appeal` | 检查关联团队和成果版本；评审批次属于项目，评审任务指向被评版本绑定 |
| 评分与成绩 | `grading_rubric`、`grading_criterion`、`grading_sheet`、`grading_criterion_score`、`grade_result` | 评分标准及维度、教师评分表、维度得分、已发布成绩和快照 |
| 支撑记录 | `stored_file`、`audit_record`、`submission_event`、通知相关表 | 附件元数据、操作审计、成果事件及业务通知 |

## 5.3 关键关联关系

| 关联路径 | 关系说明 |
| --- | --- |
| `course → course_membership → app_user` | 课程与用户为多对多关系；`course_membership` 同时记录课程角色与是否有效 |
| `course → course_project` | 一门课程可包含多个课程项目；每个项目属于一门课程 |
| `course → course_team → course_team_member` | 课程团队先形成固定成员名单；成员通过邀请和接受状态确定 |
| `course_team → project_team → course_project` | 课程团队可选定多个项目；每个课程团队与项目的组合对应项目工作团队，V14 对该组合建立唯一约束 |
| `project_team → project_team_member → app_user` | 项目团队与学生用户关联；成员状态用于判断当前团队成员资格 |
| `project_team → team_iteration → team_task / team_milestone` | 团队迭代承载任务与里程碑；任务记录负责人、计划时间和进度 |
| `project_team → submission_package → submission_version` | 提交包/版本记录团队每次正式交付；版本号和受理时间构成可追溯历史 |
| `submission_version → submission_version_material` | 一个正式版本可关联多项文件或链接材料 |
| `team_delivery → submission_review_binding → submission_version` | 团队交付状态保存最终成果与被评版本引用；评审绑定指向明确版本 |
| `review_round → review_task → review_submission` | 互评批次包含评审任务；任务指定评审学生和被评成果绑定，提交记录保存分数和评语 |
| `grading_rubric → grading_criterion`、`grading_rubric → grading_sheet` | 一份评分标准包含多个维度，也可供多个教师评分表使用。评分表记录对团队的评分并引用被评版本绑定 |
| `grading_sheet → grading_criterion_score ← grading_criterion` | 每条维度得分分别引用所属评分表和对应评分维度 |
| `grade_result.roster_id → grade_roster.id` | 成绩结果引用已确认的计分名单，保留教师评分与互评来源快照 |

| 需要区分的引用 | 保存位置 | 含义 |
| --- | --- | --- |
| 课程团队与项目团队 | `project_team.course_team_id` | 固定课程团队每选一个项目，就对应一个项目团队。历史项目团队的这项引用允许为空。 |
| 本轮当前提交 | `submission_package.current_version_id` | 每个团队迭代的提交包单独记录当前版本。重交产生新版本，并更新这项引用。 |
| 团队最终成果 | `team_delivery.final_version_id` | 指向指定或核实补定的正式成果版本，指定前允许为空。 |
| 当前被评版本 | `team_delivery.review_binding_id` | 指向教师确认的评价绑定，再由绑定指向具体成果版本。确认前允许为空。互评任务、教师评分和成绩来源可通过各自记录的绑定追溯版本。 |

## 5.4 课程团队与项目团队的区别

当前代码存在两层团队概念，不能混为一谈。`course_team` 是课程内先行组建的固定团队，负责邀请、成员确认和项目选择；`project_team` 是课程团队选定某个项目后形成的项目交付团队，承载该项目的迭代、成果、检查、互评和评分。一个课程团队可对应多个 `project_team`，因此同一队伍在不同项目中有独立的项目工作台和交付记录。

## 5.5 版本与引用数据的分离

系统将正式提交版本、团队最终指定版本、教师确认的被评版本分开保存。重交会产生新的 `submission_version`，不覆盖旧版本；最终指定和评审引用不会因新版本出现而自动替换。`review_task` 和 `grading_sheet` 等后续业务通过 `submission_review_binding` 追溯被评版本，成绩结果进一步保存评分来源快照。课程允许在限定窗口内补交，但补交时产生的最新版可能从未接受评价。把提交包的当前版本、团队的最终指定和评价绑定分别保存，既能展示最新提交，也能按评审当时引用的版本回查材料。

# 6 权限控制设计

## 6.1 权限控制原则

权限采用“平台身份 + 课程成员角色 + 资源关系 + 业务状态”的组合判断。课程角色不是用户全局固定角色，而是从当前课程的有效成员关系中查询。前端展示的角色或按钮状态不能代替后端授权。

## 6.2 认证与接口安全

- Spring Security 使用基于 Session 的 Cookie 会话认证；登录成功后建立会话，退出时清除会话 Cookie。
- 公开接口仅包括健康检查、CSRF 获取和登录等必要入口；其余 `/api/**` 接口要求已认证。
- 写操作采用 CSRF 防护。前端先 `GET /api/auth/csrf` 获取 token，登录后重新获取 token，`POST/PUT/PATCH/DELETE` 请求携带对应 CSRF 请求头。
- 未登录请求返回 401；已登录但无权限返回 403；CSRF 凭证失效也返回 403，并使用明确错误码。
- 密码使用 `BCryptPasswordEncoder` 进行编码；错误响应不返回密码、令牌、SQL 或堆栈信息。

## 6.3 课程角色与对象权限

| 角色/身份 | 主要授权范围 | 后端校验位置 |
| --- | --- | --- |
| 平台管理员 | 创建账号和课程、分配课程成员角色；管理员身份不自动绕过课程资源权限 | 用户/课程管理相关服务；课程业务仍检查有效成员关系 |
| 教师 | 本课程项目管理、助教授权、补交审批、被评版本确认、互评组织、教师评分和成绩发布 | `CoursePermission.requireTeacher`；各业务 Service 的教师角色判断 |
| 助教 | 仅检查获授权团队的成果并提出整改、复查；不能正式评分或发布成绩 | `CoursePermission.requireMember + requireTeamScope`；`InspectionService` |
| 团队负责人/组长 | 管理团队协作；代表团队正式提交、重交、最终成果指定等 | `SubmissionService.lead`；`CollaborationService` 团队管理者判断 |
| 普通学生/组员 | 本人团队任务与材料准备、被分配的互评、本人已发布成绩查询 | 成员关系校验、`SubmissionService.student`、`ReviewService` 任务归属校验、成绩查询范围 |

## 6.4 助教团队授权

助教虽具有课程 TA 角色，但不能因此查看或操作该课程全部团队。系统通过 `assistant_team_scope` 将助教用户与被授权的 `project_team` 关联。`CoursePermission.requireTeamScope` 在助教访问团队时检查该授权关系；相关列表查询也使用该范围进行过滤。

## 6.5 文件访问控制

文件由 `FileService` 管理，文件存放于非公开目录，文件名采用 UUID。个人待提交文件的下载需重新验证上传者及课程资格；教师或平台管理员身份不会自动获得个人文件访问权。正式成果材料下载还需通过团队、版本和材料归属关系检查。文件下载以附件形式返回并设置 `private/no-store` 等响应控制。

# 7 核心业务规则与执行层次

## 7.1 规则执行分层

| 规则类型 | 执行位置 | 典型内容 |
| --- | --- | --- |
| 交互提示 | Vue 页面 | 必填提示、按钮可见性、表单格式等；仅改善体验 |
| 请求校验 | Controller/参数绑定/Validation | 请求参数类型、基础格式和必需字段 |
| 权限与业务规则 | Service + CoursePermission | 课程角色、团队成员、负责人、助教范围、截止时间、项目状态、版本归属 |
| 数据完整性 | 数据库约束 + Flyway schema | 主外键、唯一约束、非空、检查约束和索引 |
| 一致性与追溯 | 事务 + AuditService/业务事件表 | 多表更新原子性、提交回执、过程记录、评分快照 |

## 7.2 项目发布与生命周期

项目由教师在课程项目池创建和维护。`ProjectService` 负责项目字段、截止时间、团队人数范围、评分维度及权重等校验，并执行发布、结束、终止或归档等状态操作。项目状态会限制后续协作、成果、检查、互评和评分操作；不是所有状态都允许继续写入。

## 7.3 组队与选题规则

- 课程团队由学生创建，组长邀请本课程学生；受邀学生接受邀请后成为有效成员。
- 同一学生在同一课程中不能同时加入多个有效/待确认团队，相关检查由 `CourseTeamService` 执行。
- 课程团队达到课程设置的人数要求后，由组长统一选择项目；默认 `required_projects` 为 2，实际数量受课程策略控制。
- 课程团队选择项目后，系统为课程团队与所选项目建立对应 `project_team`，项目工作台的数据彼此独立。
- 课程团队成员确认、选题等关键写操作在事务中执行，并校验课程处于可操作状态。

## 7.4 迭代、任务与里程碑规则

`CollaborationService` 以 `project_team` 为上下文组织团队协作。迭代包含名称、目标、顺序和计划起止日期；任务必须归属某一迭代，可关联项目要求并指定负责人；成员更新本人任务进度。迭代结束后该迭代只读，遗留任务可按规则转入后续迭代。里程碑关联迭代并保存目标日期、完成条件和状态。写操作使用团队 `revision` 等并发控制信息，并记录操作原因与前后变化。

## 7.5 成果材料、正式提交与版本规则

- 普通学生成员可以准备成果材料；正式提交、重交和最终成果指定仅限团队负责人。
- 材料准备与正式提交分离。上传材料不等于正式提交；负责人选择材料并提交后，后端校验迭代、材料归属、文件可用性和提交窗口。
- 正式提交生成新的版本记录、受理时间和回执；`requestKey` 用于识别重复请求，避免重复生成同一提交。
- 单文件大小上限为 50MB，每版文件总量上限为 200MB；链接材料需通过 URL 等格式校验。
- 最终截止前负责人可指定最终成果；截止后冻结。若截止时未指定，教师可核实材料可访问性并补定最终成果。
- 教师另行确认被评版本，后续互评和评分均引用该明确版本；更换既有被评版本需明确记录是否需要重评。
- 截止后补交需由团队申请、教师批准并设置限时窗口；授权窗口受开始/结束时间和最长时长约束。

## 7.6 助教检查规则

`InspectionService` 仅允许本课程助教执行检查。助教必须具有目标团队授权。检查记录关联团队和具体成果版本，可记录检查结论、反馈及是否要求整改。复查时需选择整改要求提出后、同一迭代中重新提交的新版本，并且一项整改检查不能重复创建多条复查结论。助教检查属于过程质量反馈，不等同于教师正式评分。

## 7.7 同伴互评规则

- 教师创建项目互评批次，确认各团队被评版本后才能自动分配互评任务。
- 自动分配以本课程相关项目学生和被评团队为基础，并尽量平衡团队被评任务负载。
- 学生只能提交分配给本人的任务；任务须处于待提交状态且未超过批次截止时间。
- 系统禁止学生评审本人所在团队的成果；评审分数须符合项目评分维度及分值上限，评语必填。
- 团队负责人可在反馈开放后规定期限内申请复核；教师审批后可安排其他符合条件的学生重评，重评结果按替代关系保留历史。

## 7.8 评分、发布与更正规则

`GradingService` 按项目评分标准加载评分维度，教师评分表记录各维度分数。成绩发布前，系统检查被评版本绑定、教师评分、互评任务完成情况、复核申请状态和计分名单等必要来源。成绩发布后形成结果版本，并保存教师评分与互评记录快照；成绩更正产生新的结果版本，保留原结果及更正原因。

项目配置的教师/互评权重以评分标准为依据，权重之和必须为 100。课堂演示示例采用教师评分 70%、有效互评均分 30%。《需求分析报告》CFG-04、FR-028 和 BR-045 已确认，只有 1 个有效团队时不开展互评，教师评分占 100%。单团队没有其他团队可评，又须遵守禁止自评的规则，因此互评不适用。当前 `GradingService.teacherWeight` 按该项目的 `project_team` 记录行数判断，恰有 1 行时采用教师 100%、互评 0%，否则使用评分标准配置。这条 SQL 没有独立的有效性过滤条件，若数据中存在不应参与计分的团队，维护时需核对项目团队行数和需求所说的有效团队数是否一致。

## 8.2 用户操作说明的引用方式

用户在浏览器中的具体操作顺序、页面名称、课堂案例数据和演示结果，以随项目提供的《系统说明》为准。本说明书不重复编写另一套操作手册。以下内容可直接作为操作说明引用：

> “用户登录平台后，教师在课程项目池发布项目；学生进入组队与选题完成团队创建、邀请确认和统一选题；团队在迭代与任务中开展分工协作；组员准备材料，由组长在成果与版本中正式提交；助教对获授权团队的成果进行检查并提出整改意见；教师确认最终成果和被评版本后组织同伴互评并完成教师评分，最后发布成绩。”

详细页面入口、课堂案例的具体时间、队伍名称、提交版本及成绩数据，请参见《系统说明》第 2—5 页。系统设计说明书关注后台如何支撑这些操作，而不是替代《系统说明》。

## 8.3 版本引用链示例

一次成果交付的关键引用链为：团队准备材料 → 负责人正式提交生成 `submission_version` → 团队在截止前指定 `final_version_id`，或教师截止后核实补定 → 教师创建 `submission_review_binding` 指定被评版本 → `review_task` 引用该 binding → `review_submission` 保存评审结果 → `grading_sheet` 引用当前 binding → `grade_result` 保存发布成绩及来源快照。该链路确保后续评价可追溯到明确的成果版本。

## 8.4 正式提交成果的处理顺序

团队负责人选好已准备的材料后，页面向 `POST /api/submissions/teams/{team}/versions` 发起正式提交。

| 步骤 | 后端如何处理 |
| --- | --- |
| 1. 核对身份与权限 | `SubmissionController` 取得会话用户。`SubmissionService` 锁定项目团队记录，并检查负责人权限和请求参数。 |
| 2. 识别重复提交 | 按团队和请求编号查询已有版本。内容相同则返回原版本和回执，内容不同则返回 HTTP 409。 |
| 3. 校验新提交 | 检查团队数据版本、迭代、材料和提交窗口。材料校验后，以实际受理时间再次检查窗口。 |
| 4. 保存版本和过程记录 | 在事务中写入新版本与材料快照，更新提交包的当前版本，记录过程事件和审计信息，并更新团队数据版本。 |
| 5. 返回结果 | 成功时返回版本和回执。失败时返回错误信息，因失败而回滚时一并撤销本次事务中的数据库变更。 |

正式提交或重交会新增版本，并更新本轮提交包的当前版本。最终成果指定、被评版本确认和重复请求的处理细节分别见 §5.5 和 §9.3。

# 9 接口与异常处理设计

## 9.1 接口约定

所有业务接口以 `/api` 开头。登录采用表单请求；登录后通过 Cookie 会话维持身份。接口统一响应结构为 `code`、`message`、`data`；文件下载接口直接返回附件流。接口清单与请求字段以 `docs/接口约定.md` 及各 Controller 为准。

| 接口类别 | 典型路径 | 用途 |
| --- | --- | --- |
| 健康检查 | `GET /api/health` | 检查服务状态、运行模式和服务器时间 |
| 认证 | `GET /api/auth/csrf`；`POST /api/auth/login`；`GET /api/auth/me`；`POST /api/auth/logout` | CSRF 获取、登录、当前用户和退出 |
| 课程 | `GET /api/courses`；`GET /api/courses/{id}` | 当前用户课程列表和课程详情 |
| 成果文件 | `POST /api/files`；`GET /api/files/{uuid}` | 个人待提交材料上传与受限下载 |
| 业务模块 | `/api/courses/{courseId}/projects`、`/api/collaboration`、`/api/submissions`、`/api/reviews`、`/api/grades` | 各业务模块接口 |
| 正式提交与回执 | `POST /api/submissions/teams/{team}/versions` 和 `GET /api/submissions/teams/{team}/receipts/{key}` | 提交携带 `revision`、`iterationId`、`materialIds`、`summary` 和 `requestKey`，返回版本及回执。也可以用请求编号查询回执 |
| 审计 | `GET /api/courses/{id}/audit` | 教师查询课程操作记录 |

## 9.2 异常处理

业务规则失败时，Service 抛出 `BusinessException`，由 `GlobalExceptionHandler` 转换为统一错误响应。常见情况包括未登录（401）、无课程或对象权限（403）、状态冲突或重复操作（409）以及参数/业务校验失败（400）。前端根据 HTTP 状态和业务 code 展示提示，不应把后端异常堆栈直接呈现给用户。

## 9.3 并发与幂等

正式提交时，后端在事务中锁定项目团队记录。校验负责人权限和基础参数后，按团队与 `requestKey` 查找已有提交。内容摘要由提交人、迭代、去除首尾空白的成果说明以及排序后的材料编号计算，材料排序变化不会改变摘要。数据库对 `(team_id, request_key)` 和 `(package_id, version_no)` 分别设置唯一约束。

| 场景 | 服务端处理 |
| --- | --- |
| 同一团队、同一请求编号、同一提交内容 | 返回原版本和回执。已受理请求在校验页面 `revision` 和当前提交窗口之前返回，因此响应丢失后可以用相同请求编号重试 |
| 请求编号相同，但内容不同 | 返回 HTTP 409，业务错误码 `REQUEST_KEY_REUSED` |
| 新请求的 `revision` 已过期 | 返回 HTTP 409，业务错误码 `STALE_WORKSPACE`，提示刷新后再操作 |
| 正式提交写入失败并导致事务回滚 | 本次写入的版本、材料快照、提交包引用、过程事件、团队修订号和同事务审计记录一起回滚。此前准备材料时已保存的附件仍由材料管理流程处理 |

3. 第二个窗口执行：`powershell -ExecutionPolicy Bypass -File .\scripts\frontend.ps1`，启动前端，默认端口 5173。
4. 浏览器访问 `http://127.0.0.1:5173`；后端健康检查地址为 `http://127.0.0.1:8080/api/health`。

首次运行会安装/解析项目依赖并由 Flyway 建立数据库结构；demo 模式初始化本地演示账号。演示账号及密码仅用于本地开发，生产模式不应使用演示账号。

# 11 设计约束、当前边界与后续注意事项

## 11.1 当前实现边界

- 当前互评按项目组织；课程内跨项目互评在 README 中明确标注为尚待调整。
- 本地课程演示采用 H2 文件数据库；PostgreSQL/Docker 为可选部署方式，二者的部署配置与演示数据初始化方式不同。
- 演示账号只用于本地开发；正式环境不应默认创建演示账号或沿用演示密码。
- 部分功能在《系统说明》中列为留待后续独立演示，例如里程碑、匿名反馈查看、成绩导出与更正等；不能仅凭主流程演示完成就声称这些独立操作均已验收。
- 接口约定文档中指出，文件内容扫描等能力不属于当前上传校验范围；对文件上传的描述应以当前代码实际校验为准。
- 框架与后续接入文档保留了早期框架阶段记录；当前模块实现情况应优先以完整项目源码、最新 README 和当前数据库迁移版本为准。

## 11.2 设计与维护注意事项

- 新增业务功能时，应同时考虑数据库迁移、实体/查询、Service 规则、Controller 接口、前端 API/页面和集成测试。
- 已执行的 Flyway 迁移脚本不应直接修改；结构调整应新增后续版本迁移。
- 业务权限必须放在后端 Service 层执行，前端角色判断只作为显示优化。
- 任何涉及正式提交、最终成果、评审或成绩的修改，都应保留版本引用和操作依据，避免覆盖历史。
- 跨模块读写应复用共享项目/团队数据和权限服务，避免产生第二套不一致的数据源。
- 关键业务写操作应在事务中完成并记录审计/业务事件；涉及附件时需同时考虑数据库事务与文件落盘清理。
